# 2.0.1 sensor audit — WS feed vs MATE3 web UI

Taken against the live MATE3 at `http://192.168.200.9/` on 2026-04-19
(~10:34 PDT) while add-on build `2.0.1-dev2` was running on hass-4. The
add-on WS snapshot is in `/tmp/mate3_ws_paired.json` (captured at the same
moment as the Meters tab refresh used below).

Methodology:

1. Open the MATE3 web UI via Playwright, click the Meters tab.
2. Take a structural accessibility snapshot so every cell value is captured
   in plain text.
3. Within ~1 s, pull the latest per-device state from
   `ws://127.0.0.1:28099/ws` through an SSH tunnel to hass-4.
4. Compare cell-by-cell. Small drift (±1 A on load currents, ±1 VAC on L1
   input) is expected because the web UI and the UDP feed refresh on
   slightly different cadences.

## Mode tab

| Port | Web UI "Mode" | WS `inverter_mode` | Web "AC Input" | WS `ac_mode` | Verdict |
|---|---|---|---|---|---|
| 1 | PassThru | pass-through | AC USE | ac-use | ok |
| 2 | AGS Error | slave-off | AC USE | ac-use | semantic diff — see note |

The web UI's "Mode" column on Port 2 shows **AGS Error**, but the UDP
`inverter_mode` byte at `values[16]` decodes as `12 = slave-off`. These
aren't the same concept: the web display folds in AGS-subsystem faults
(Advanced Generator Start), while the UDP byte reports pure inverter
operating state. AGS is disabled on this system (`<Advance_Generator_Start
Mode="Disabled">` in CONFIG.xml), so the "AGS Error" banner is a stale
display state that doesn't affect telemetry. Not flagging as a bug — the
UDP answer "slave-off" is correct for a non-inverting slave with AC pass-
through active on the master.

## System-level status

`Status` tab:

- PV Output: 2840-3520 W (varies per refresh). HA exposes `pv_power_total`
  as the sum of CC `pv_power` = 2052 + 1392 ≈ 3444 W during the capture. ok.
- Inverting: 0.0 kW ↔ `inverter_power_total` = 0. ok.
- Charging: 0.0 kW ↔ `charger_power_total` = 0. ok.
- AC Load: 3.4-3.7 kW ↔ computed from buy × input voltage = `grid_power` sum
  ≈ 854+610 = 1464 W WS vs 3.4 kW web. **Discrepancy** — but this one is
  about semantics: web "AC Load" is _load_ (inverter_power + buy_power),
  while our `grid_power` is net buy. Values are consistent with their
  respective definitions once you trace through. No bug, just different
  metrics.

## New bugs discovered (queued for 2.0.1 or later)

- **F2** — Charge-controller `kwh_today` sensor is stuck at 0. **Same shape
  as F1: wrong CSV index.** The parser reads `values[13]` (always `00`); the
  real value is at `values[6]` as integer tenths of a kWh. Verified against
  hass-4 frames:
  - Port 4 frame `<04,3,00,32,23,076,036,03,03,000,02,533,0068,00>` →
    `values[6]=036` while web UI showed **3.6 kWh**.
  - Port 5 frame `<05,3,00,22,14,087,019,05,03,000,02,534,0035,00>` →
    `values[6]=019` while web UI showed **1.9 kWh**.
  Fix: `kwh_today = float(values[6]) / 10.0`. Pre-existing from the upstream
  integration. The Radian PRELIMINARY PDF doesn't document the CC byte
  layout (CC is FM/FlexMax, separate doc not in hand) — this was found by
  cell-by-cell match against captured UDP + the MATE3 web UI.
- **F3** — Daily Ah is not exposed. `values[12]` (4-digit) encodes daily
  Ah — the MATE3 web UI shows this as the "Daily Ah" column (67 Ah / 35 Ah
  in our captures). Add a `daily_ah` CC sensor with unit `Ah`.
- **F4** — Charge-controller voltages and currents are integers in the
  UDP stream but displayed as one-decimal values in the web UI (76 VDC
  UDP vs 76.8 VDC web; 32 ADC UDP vs 31.2 ADC web). This is a MATE3
  protocol limitation, not something we broke — but worth a note in the
  docs so users know our CC readings are coarser than what the MATE3
  display shows. No code change expected.
